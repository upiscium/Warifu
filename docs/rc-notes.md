評価用のインストールアーカイブは `nextcloud_gateway-0.2.0-rc.1.tar.gz`（39,146 bytes）です。SHA-256 は `62cd94305082333345c8fed60636b760b134eaf3ca069373a06fcfa137915e83`。同じ配布元の `SHA256SUMS` と照合してください。チェックサムは署名の代替ではありません。

## 変更された処理上限

既定値はすべて上限です。システム設定 `nextcloud_gateway_limits` とユーザー設定 `nextcloud_gateway/limits` では、既知キーの正整数で既定値より下げられます。ユーザー設定でシステム上限を引き上げることはできません。不正な設定は要求を `503` で拒否します。

| 項目 | v0.1.0 | v0.2.0-rc.1 |
| --- | ---: | ---: |
| 協調的な要求時間 | 30 秒 | 300 秒 |
| 1ファイル | 64 MiB | 50 GiB |
| 1要求の累積ハッシュ量 | 256 MiB | 1024 MiB |
| 1要求のハッシュ回数（再計算含む） | 1024 | 1024 |
| PROPFIND 項目数（コレクション自身を含む） | 512 | 2048 |
| ユーザーごとの並行処理要求 | 4 | 4 |

大きなファイル上限は大きなハッシュ予算を意味しません。50 GiB ファイルはサイズ上限内でも、全体の SHA ETag 計算が累積ハッシュ予算を超えれば `503 hash_budget` になります。Range GET もファイル全体をハッシュします。上限超過は 413（サイズ）または 503（処理予算）、並行枠超過は429です。時間制限は協調的で、停止しないブロッキングI/Oを強制終了しません。

## TTL・ストレージ・運用

- `filelocking.ttl` は `max(60, 4 × request_seconds)` 以上が必要です。既定の300秒では最低1200秒です。満たさない場合は503となります。
- Redis の `timeout` と `read_timeout` は有限の正数で、`min(5, request_seconds)` 以下が必要です。Redis Cluster は対象外です。
- PUT本文をロック取得前に上限付きで読み込みます。chunk の断片と組み立て後にもサイズ上限を適用します。GET/PUTの一時領域は並行要求分を含め別途確保してください。
- Nextcloud標準Files DAVの登録フォルダに限定します。`allowed_roots` は認可境界ではなく、他の入口を閉じません。専用ユーザー・小さな専用フォルダから始め、外部入口を制御してください。
- 対象は固定ランタイム、通常の非暗号化ローカルホーム、対応ロック構成です。外部ストレージ、暗号化、共有リンク、他アプリ・ホスト直接書込み、Nextcloudコア更新への適合は保証しません。

## このアーカイブで確認したこと

- 固定したNextcloud 35.0.3の隔離環境に新規導入し、`v0.1.0` からも標準 `occ upgrade` で更新できました。元のApp Password・登録先・ノート本文を維持し、正しい条件で更新204、古いETagで412、再取得200を確認しました。
- PUTの保存後に強いETagを計算する分のハッシュ予算を、保存前に確認します。小さな個別上限での実HTTP試験では、不足する上書きは503で元の本文を保持し、不足する新規作成は503で対象は404のままでした。I/O障害等による不確定な失敗まで「変更なし」とはみなさず、再試行前に対象を読み戻してください。
- 単体674 assertions、DBロック構成162件・Redisロック構成164件の回帰試験が成功しました。50 GiBの実転送、実NAS更新、今回の版でのMariaDB再試験は行っていません。
