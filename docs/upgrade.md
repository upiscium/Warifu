# 0.1.0-rc.3 から 0.1.0 への更新

この手順は、同一アプリ ID `nextcloud_gateway` の手動更新です。[新規インストールガイド](install-nextcloud.md)と同じ前提を満たすこと、配布アーカイブのSHA-256が一致することを確認してください。

## 更新前

1. 対象環境が固定ランタイム（Nextcloud 35.0.3、PHP 8.5.12）および対応ストレージの範囲内であることを確認します。範囲外なら更新を進めず、適合性を別途評価してください。
2. アプリの設定と現在の状態を記録します。アプリの有効状態、登録ユーザー／`allowed_roots`、アプリディレクトリ名を確認します。
3. **すべての書込み元を停止**します。Web・DAVクライアント、cron、外部writerを停止し、進行中の書込みを完了させます。
4. Web実行ユーザーで `php occ maintenance:mode --on`。全ワーカーを停止・排出してから、DB・設定・データ・rc.3コードを同じ時点でバックアップし、隔離先で復元できることを確認します。アプリの有効状態は維持します。

## アプリの置換とアップグレード

1. 展開先とは別の一時ディレクトリに GA アーカイブを展開します。展開後、想定した `nextcloud_gateway` アプリのルート構造を確認します。
2. 同じファイルシステム上の**Web公開範囲・アプリ探索パスの外**に退避先を用意し、既存アプリディレクトリを退避します。ステージ済みディレクトリを `nextcloud_gateway` に移動します。既存ディレクトリへのoverlay展開はしないでください。所有者・権限を確認します。
3. Nextcloud の標準 `occ upgrade` を実行します。`--force` は付けません。終了コードと出力を確認し、失敗時はその場で先へ進まず、下記の復旧手順に従います。
4. `php occ config:app:get nextcloud_gateway installed_version` が `0.1.0`、従来の有効状態と `allowed_roots` が維持されていることを確認します。退避したコードはWeb公開範囲・アプリ探索パスの外に保管してください。
5. メンテナンスモードを解除し、全Webワーカーを新しいコードと設定で起動します。合成ファイルでDAVの読み書き・ETag・古い条件の412を確認してからwriterを再開します。

## ロールバックと復旧

- **迅速な機能ロールバック:** writerを止め、全Webワーカーを排出します。`php occ config:app:set nextcloud_gateway experimental_enabled --value=no` を実行し、全ワーカーを再起動します。認証済みGETが200、本文が不変、Gatewayヘッダーがなく、ETagがネイティブに戻ったことを確認します。`occ` の成功だけで切替完了とはしません。クライアントにETagを再取得させてから書込みを再開します。これはデータの巻戻しではありません。
- **完全な復旧:** アップグレード後に状態を戻す必要がある場合は、writer を停止し、メンテナンスモードで、事前に取得したアプリデータとデータベースを同一時点の整合バックアップから一緒に復元します。コードも対応するバックアップ時点のものに戻し、整合性を確認してから再開します。
- **禁止:** 更新後の DB に対して、古いアプリコードをそのまま配置して in-place downgrade しないでください。単に旧アプリディレクトリへ戻すことは、DB やデータの復元にはなりません。

復元後もアプリを無効のままにして原因調査を行えます。復元手順やバックアップの整合性が不明な場合は、書込みを再開せず、Nextcloud 管理者の復旧手順に従ってください。
